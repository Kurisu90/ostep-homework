
# 總覽

這份作業要介紹 `fsck_zh.py`，一個簡單的檔案系統模擬器（`fsck.py` 的
中文版本）。如果你已經熟悉檔案系統實作那一章介紹過的 `vsfs.py`
模擬器，會比較容易上手，但這不是必要條件。

這個工具會改變檔案系統在磁碟上的狀態，然後留給你（使用者）自己去
偵測問題出在哪裡，就像真正的檔案系統一致性檢查工具（例如 fsck）會做
的事情一樣。這裡使用的檔案系統，是以之前章節介紹過的簡化版 VSFS 為
基礎。這個工具會先產生一個磁碟上的檔案系統；接著，不論是隨機地，
還是透過更具體的控制，工具會改變檔案系統其中一個部分在磁碟上的狀態。

對你來說，挑戰就在於：找出檔案系統中哪個部分的磁碟狀態被改變了，因而
變得不一致。在許多情況下，這個問題應該不難被發現；但在其他情況下，
可能就沒那麼容易了。

我們直接進入細節。以下是這個工具的一次執行範例：

```sh
prompt> ./fsck_zh.py -S 1
...
檔案系統的最終狀態：

inode 點陣圖 1000100010000001
inode 內容   [d a:0 r:4] [] [] [] [d a:12 r:2] [] [] [] [d a:6 r:2] [] [] []
             [] [f a:-1 r:2] [] [f a:-1 r:1]
資料點陣圖   1000001000001000
資料區塊     [(.,0) (..,0) (g,8) (w,4) (m,13) (z,13)] [] [] [] [] []
             [(.,8) (..,0) (s,15)] [] [] [] [] [] [(.,4) (..,0)] [] [] []

你能看出檔案系統是怎麼被毀損的嗎？

prompt> 
```

在這個例子裡，我們把 `-S` 旗標設為 1 來執行這個工具（原因稍後就會
清楚）。要理解磁碟狀態發生了什麼變化、以及可能存在的不一致，首先得
了解這個檔案系統的格式。它（一如先前所承諾的）非常簡單。

首先，有一個 inode 點陣圖，用來標記每個對應的 inode 是已配置（1）
還是空閒（0）；在這個例子中，一共有 16 個 inode，其中編號 0、4、8、
13、15 被標記為已配置。

第二，有 16 個 inode。未配置的 inode 顯示為空括號──`[]`──而已配置
的 inode 則會有像上面 `[f a:-1 r:1]` 這樣的內容。每個已配置的 inode
有三個欄位：第一個是檔案的類型，'d' 代表目錄，'f' 代表一般檔案；第
二個是位址欄位 'a'，它要嘛指向單一個資料區塊（在這個陽春的檔案系統
裡，檔案／目錄最多只能有一個區塊），要嘛是 -1，代表這個檔案是空的；
第三個是參照計數，對一般檔案來說，代表這個檔案在檔案系統中被連結
（link）的次數，對目錄來說，則代表這個目錄底下有幾個子目錄。

第三是資料點陣圖。跟 inode 點陣圖很像，它標示檔案系統中每個資料區塊
是已配置還是空閒。

最後是資料區塊本身。對一般檔案來說，資料區塊的內容是任意的（但通常
只放一些簡單的東西，例如一個字母；在現實世界中，這裡會是實際的檔案
資料區塊），而目錄的內容則是一份結構化的 (name, inode 編號) 配對清單。

在這個檔案系統中，根目錄永遠是 inode 編號 0；你可以從這裡開始，
逐步建立起對整個檔案系統及其內容的理解。

這個檔案系統剛好包含以下的檔案與目錄：
```sh
  目錄：'/', '/g', '/w'
  檔案：'/t', '/m', '/w/p'
```

你看得出為什麼嗎？花點時間，從根目錄開始，試著自己想清楚。如果想不
出來，嗯，這份作業對你來說可能會有點吃力。

現在，我們來看看不一致的部分。這個檔案系統裡剛好有一個具體、單純的
不一致之處，你看得出來嗎？

花了一些時間之後，加上 `-c` 旗標執行看看，看你猜得對不對：

```sh
prompt> ./fsck_zh.py -S 1 -c

檔案系統的初始狀態：

inode 點陣圖 1000100010000101
inode 內容   [d a:0 r:4] [] [] [] [d a:12 r:2] [] [] [] [d a:6 r:2] [] [] []
             [] [f a:-1 r:2] [] [f a:-1 r:1]
資料點陣圖   1000001000001000
資料區塊     [(.,0) (..,0) (g,8) (w,4) (m,13) (z,13)] [] [] [] [] []
             [(.,8) (..,0) (s,15)] [] [] [] [] [] [(.,4) (..,0)] [] [] []

毀損資訊：：inode 點陣圖的第 13 個 bit 被毀損

檔案系統的最終狀態：

inode 點陣圖 1000100010000001
inode 內容   [d a:0 r:4] [] [] [] [d a:12 r:2] [] [] [] [d a:6 r:2] [] [] []
             [] [f a:-1 r:2] [] [f a:-1 r:1]
資料點陣圖   1000001000001000
資料區塊     [(.,0) (..,0) (g,8) (w,4) (m,13) (z,13)] [] [] [] [] []
             [(.,8) (..,0) (s,15)] [] [] [] [] [] [(.,4) (..,0)] [] [] []

prompt> 
```

從輸出可以看到，inode 點陣圖的第 13 個 bit 被改變了，把原本已配置的
inode 標成了空閒。你可以透過查看 inode 13 本身來發現這個不一致：它
長這樣：`[f a:-1 r:2]`（一個一般檔案，但沒有配置資料區塊）。你也知道
這個檔案在根目錄底下（/m）。因此，得出「是 inode 點陣圖被改動了」這
個結論並不困難。

還有許多其他可能的毀損方式（不過這個工具每次只會引入一種狀態改變，
好讓事情單純一點）。做這份作業，你就會慢慢認識它們。

這個工具還有其他一些可用的旗標：

```sh
prompt> ./fsck_zh.py -h
Options:
  -h, --help            show this help message and exit
  -s SEED, --seed=SEED  第一個隨機種子（用來產生檔案系統）
  -S SEEDCORRUPT, --seedCorrupt=SEEDCORRUPT
                        第二個隨機種子（用來產生毀損）
  -i NUMINODES, --numInodes=NUMINODES
                        檔案系統中的 inode 數量
  -d NUMDATA, --numData=NUMDATA
                        檔案系統中的資料區塊數量
  -n NUMREQUESTS, --numRequests=NUMREQUESTS
                        要模擬的請求數量
  -p, --printFinal      列印最終的檔案／目錄清單
  -w WHICHCORRUPT, --whichCorrupt=WHICHCORRUPT
                        指定要執行的毀損類型
  -c, --compute         幫我計算答案
  -D, --dontCorrupt     真的讓檔案系統毀損
```

（`-h, --help` 這一行是 optparse 套件內建、寫死的英文字串，未做在地化；
另外要提醒一下，`-D` 選項印出的英文說明文字其實跟它的名稱 `dontCorrupt`
矛盾──這是原始 `fsck.py` 裡就存在的小瑕疵，這裡照實保留、只是照樣
翻譯，並未修正。實際上 `-D` 的效果，跟下面段落描述的一樣，是關閉
毀損。）

之所以有兩個隨機種子，值得說明一下。第一個 `-s`，用來產生不同的隨機
檔案系統。第二個 `-S`，則用來插入不同的檔案系統狀態改變（也就是
「毀損」）。因此，你可以先產生一個特定的隨機檔案系統，然後在它上面
嘗試一堆不同的隨機毀損。

其他幾個旗標則是用來控制檔案系統的大小（`-i` 和 `-d`），還有多少個
檔案操作會被套用到檔案系統上（`-n`）。`-p` 旗標會印出（未毀損的）
檔案系統內容；`-w` 旗標讓你指定特定的毀損類型（主要是用來測試）；
`-D` 旗標則會關閉毀損，讓你可以檢視一個完整、未毀損的檔案系統。
